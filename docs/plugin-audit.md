# 🔌 Plugin interface audit

Reviewed local Config structs, generated HCL2 schemas, main registration, restart logic, guest actions, docs/examples and reports on 2026-11-19. The registered component is `plugin.DEFAULT_NAME` in each custom plugin, so its HCL name is the required-plugin name without a repeated suffix. All use the builder-provided WinRM communicator and require elevated native Windows PowerShell 5.1; no second connection mechanism is introduced.

The four custom plugins target Server 2019 build 17763, 2022 build 20348 and 2025 build 26100, including Core/Desktop. These are implemented support targets, not proof of live qualification. Hardening selects ws2019-member, ws2022 or ws2025-2602, rejects unsupported roles/releases and checks lifecycle. The audit found no reason to exclude Windows Server LTSC: its LTSC edition rejection applies to client edition IDs, not these server builds. Optimization/cleanup similarly reject domain controllers or unknown server base builds.

No ordinary custom-plugin setting is mandatory in isolation except that features needs at least one operation. limit_access requires source. This factory opts into failure on errors, read-back validation and owned restarts. Cleanup artifact paths must stay within its fixed staging/Temp roots or its small exact-file allowlist; arbitrary system directories are rejected. Old temporary files are age filtered; recent factory-owned files are explicitly manifested.

Optimization and hardening also run with their implemented dry_run option after updates/restart. Their separate validation reports must have zero failed/pending settings before the release manifest is issued. Compatibility deferrals remain explicit rather than being counted as fully compliant controls.

`packer init` successfully downloads Hyper-V 1.1.5 and rgl/windows-update 0.18.4. It returned **no release found** for all four custom sources. `Install-LocalPlugins.ps1` builds the existing sources without editing them, clears the development prerelease suffix as their docs prescribe, installs them with `packer plugins install --path`, and records commit, dirty state and binary hash. Once installed in PACKER_PLUGIN_PATH, init and full validation succeed. Local compilation is a dependency workaround, not a signed release certification. CI pins source commits. Private or unpublished source commits require runner/checkout access.

The unavailable packer-plugin-windows-update repository was not recreated and no schema was invented. The user approved the installed upstream alternative. Offline approved OOB packages are the one small servicing bridge: upload a hashed MSU, install it under SYSTEM with WUSA through a windows-restart command, and wait for reconnection before the next prerequisite. No promise is made that an OOB package appears in Windows Update.
